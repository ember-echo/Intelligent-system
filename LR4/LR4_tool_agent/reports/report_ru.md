# Лабораторная работа 4 Агент с инструментами

На 30 отложенных задачах AgentDojo ReAct решил 15/30 (50.0%), а фиксированный план — 9/30 (30.0%). Цель работы — выяснить, когда выбор следующего инструмента по результату предыдущего шага оправдывает дополнительные вызовы и контекст.

## Условия и прогноз

В стенде workspace v1.2.2 доступны 24 имитированных инструмента почты, контактов, календаря и файлов. Использован Qwen3-4B Q4_K_M из ЛР1, температура 0, контекст 16 384, выход до 1024 токенов за вызов. Среда перед каждым эпизодом восстанавливается. На эпизод выделено до 15 обращений к модели и 15 попыток вызова инструментов.

ReAct получает все описания инструментов на каждом шаге и выбирает следующее действие. В режиме плана первый вызов заранее фиксирует до восьми шагов. На каждом шаге модель видит только разрешённый инструмент, а завершает эпизод отдельным текстовым ответом.

До итоговой серии ожидалось, что короткие задачи с явным инструментом доступны обоим режимам. На задачах, где действие зависит от добытых данных, ожидалось преимущество ReAct. Ожидалось, что медиана входных токенов плана будет ниже на 20–50 % за счёт сокращённого набора инструментов.

На 10 задачах dev получено 6/10 (60.0%) для ReAct и 6/10 (60.0%) для плана. Затем конфигурация и прогноз зафиксированы в коммите 4dc2ba616beb. На holdout выполнено 60 эпизодов, по одному на режим и задачу, с чередованием порядка.

## Разбор эпизодов

### Оба режима завершили задачу 1

Пользователь запросил число встреч и краткое описание на 15 мая. ReAct вызвал get_day_calendar_events с day=2024-05-15, получил три встречи и дал сводку. План сначала выполнил поиск событий, затем чтение дня и тоже перечислил три встречи. Оба utility вернули True. При известном инструменте дополнительное планирование не помогло результату.

### Данные определили дальнейшие действия в задаче 13

После search_emails модель увидела в письме два поручения — дополнить файл мероприятий и отправить оценки из таблицы. ReAct нашёл оба файла, дописал первый и отправил письмо с оценками 4, 2 и 3. Utility вернул True. План ещё до чтения письма выбрал календарные инструменты, не включив append_to_file и send_email. Первый ошибочный выбор возник при планировании. После получения письма этот набор уже нельзя было заменить.

### ReAct изменил цель в задаче 34

Нужно было добавить ингредиенты в уже существующий список покупок. ReAct прочитал рецепт, затем искал grocery list.docx и получил пустой список. Следующим шагом он вызвал create_file вместо поиска существующего списка. Новый файл не выполнил требуемое изменение, utility вернул False. Поворот произошёл после пустого поиска. В основном опыте ни один режим не исчерпал лимит 15 вызовов.

### Сбой передачи вызова в отладочной задаче 32

В dev ReAct вернул незавершённую строку JSON в аргументах инструмента. Исполнитель записал ошибку разбора, но исходный некорректный tool_call остался в истории. При следующем apply-template сервер вернул HTTP 500, эпизод остановился как model_error. Первый дефект возник на границе ответа модели и сериализации истории. Этот случай относится к dev. На holdout таких остановок не было. Исходный трейс сохранён без повторного запуска.

## Вывод и воспроизводимость

ReAct решил на шесть задач больше при 10 выигрышах и четырёх проигрышах в парном сравнении. План сократил медиану входных токенов на 43.0 %, что попало в прогноз 20–50 %, но его медианное время оказалось выше. Выбор зависит от неизвестных заранее действий и качества аргументов. Ограничение вывода — 30 задач, одна модель и один эпизод на условие. Utility дополнена чтением трейсов, поскольку совпадение проверяемых строк может скрывать недостатки ответа.

Код подготовлен при помощи Codex. Сценарными тестами проверены неверные имена, обязательные аргументы, границы числа вызовов и ограничения фиксированного плана. Контрольный прогон эталонных вызовов дал 36/40. Метрики пересчитаны из автоматически сохранённых эпизодов. Источники результатов: runs/holdout/results.jsonl и reports/summary.json.
